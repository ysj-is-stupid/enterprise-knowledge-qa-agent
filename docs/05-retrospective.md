## 3. 最难的问题

### 3.1 既保持动态决策，又设置不可绕过的安全边界

如果执行器把路径写死，无法满足 ReAct；如果把全部控制交给模型，又可能漏读冲突文档、伪造引用或提前回答。

最终做法是让模型选择搜索、读取、追问和完成，执行器只设置安全守卫。测试模型可以尝试提前完成，但会收到结构化校验错误，再根据新观察调整动作。

### 3.2 冲突不能简单按日期裁决

企业制度的“较新”不必然表示“替代”，范围更窄也不必然表示“特例”。因此系统只接受明确的 `supersedes`，或经过源目标绑定、范围包含关系和问题条件三重校验的 `rule_overrides`。数字优先级仅在范围相同时生效；缺少可靠依据时必须展示双方原文并追问。

### 3.3 小型中文检索的误召回控制

不使用 embedding 模型可以保持离线和零依赖，但字符片段与词项评分容易被公共词影响。实际运行中的食堂问题暴露了这个缺陷。通过查询全词项权重归一和最低阈值门槛，误召回得到修复。

### 3.4 引用存在不等于语义一定正确

仅检查原文片段存在，仍可能出现“引用是真的，但不支持声明”的情况。最终不仅增加数字一致性、未读候选和冲突阻断，还把成功声明限制为可逐句映射的原文或已定义等价变换，并输出支持证书。系统不猜测自由释义，无法证明时宁可拒绝完成。

### 3.5 Python 3.13 干净环境不预装 setuptools

全量验证发现新 venv 中只有 Python，editable 安装使用的 setuptools 构建后端不可用。原 README 又指定了 `--no-build-isolation`，导致 pip 无法补齐构建依赖。最终把零依赖的 `PYTHONPATH=src` 方式设为首选离线步骤，editable 安装仅作为可选方式。

## 4. 学习收获

- ReAct 的价值不在日志格式，而在工具观察确实改变下一动作。
- 检索质量需要用资料外问题和改写问题同时约束，不能只测命中率。
- 冲突处理需要区分“发现冲突”和“有依据地裁决冲突”。
- 让执行器从证据对象生成引用，比让模型输出文档 ID 和原文更安全。
- 资料替换测试可以有效发现答案是否被写死在规则或 Mock 中。
- 离线 Mock 与真实模型评估必须分开表述，否则容易夸大测试结论。

## 5. 已知限制与未完成部分

1. 真实模型验证了六类必验场景与两类扩展路径，共 8 条合成路径；尚未形成真实企业数据或大样本质量评估。
2. 未进行线上部署、Web 界面或 HTTP API 开发。
3. 已实现基础部门 ACL 过滤，但未接入企业身份认证、外部身份提供商或审计持久化；调用方仍需可信地提供部门上下文。
4. 未接入向量数据库、重排序模型或大规模文档切分。
5. 任意自然语言释义仍不在证明范围内；系统用逐句原文证明契约规避该风险，代价是自由释义可能被保守拒绝。
6. 长历史已改为有原文、消息序号和哈希的情景记忆检索，不再使用不可溯源摘要；大规模真实对话召回率仍需持续评测。
7. 文本支持度仍作为前置风险信号，但最终成功与否由逐句支持证书决定。
8. GitHub 仓库 URL、最终 commit SHA 和评审账号权限按提交者要求暂缓处理。

## 6. 下一步

按优先级建议：

1. 使用更多真实业务式改写与冲突样本建立统计评测集。
2. 对真实模型输出增加供应商结构化输出约束，并持续测试兼容差异。
3. 使用更多改写问题校准检索阈值，并记录召回率和误召回率。
4. 接入可信身份源和用户级访问控制。
5. 在大规模资料环境增加向量召回和交叉编码器重排序。
6. 增加真实对话中的澄清回复续接，而不仅是单次任务输出。

## 7. 总结

项目优先完成了最影响可信度的核心链路：真实读取资料、让观察改变动作、在冲突和失败时停止、让答案随资料变化。界面和部署被有意延后，没有挤占核心检索与证据验证时间。
