# 企业知识问答 Agent：阶段 1 技术选型记录

## 1. 阶段目标

本阶段只确定技术路线、运行方式、模型与工具边界、检索思路、输出协议和验证方式，不进入总体方案设计与代码实现。

项目目标是帮助员工从带文档 ID、版本日期和适用范围的企业制度或产品资料中获得可靠答案。系统必须基于实际读取的资料回答，并能处理文档冲突、资料不足、上下文追问和工具失败。

## 2. 最终技术选型

- 语言：Python 3.11+
- 运行方式：CLI
- Agent 实现：原生状态机式 ReAct 循环
- 真实模型：OpenAI-compatible Chat Completions HTTP 接口
- 离线模式：确定性 Mock 决策模型
- 文档存储：本地 JSON 合成知识库
- 检索：关键词、中文字符片段、领域同义词及元数据加权的混合检索
- 测试：Python 标准库 `unittest`
- Trace：结构化 JSON
- 外部依赖：核心离线功能只使用 Python 标准库

## 3. 框架取舍

本项目不采用 LangGraph、Google ADK 或 AgentScope，选择原生实现 ReAct 执行循环，原因如下：

1. 项目规模较小，原生循环足以表达“模型选择动作 → 执行工具 → 观察结果 → 模型调整下一步或结束”。
2. 动作、工具结果、停止条件和引用校验逻辑可直接审查，便于证明动态决策不是预设日志。
3. 更容易注入工具失败、替换知识库并验证回答是否随资料变化。
4. 减少评审环境中的依赖安装和框架版本差异。

框架名称本身不构成加分项。本项目优先保证核心链路可运行、可解释、可测试。

预期执行形态：

```text
模型选择动作
    ↓
执行 search_docs / read_doc
    ↓
记录工具观察
    ↓
模型根据观察选择下一动作
    ↓
补充检索 / 读取原文 / 追问 / 完成
```

预设执行骨架只限制合法动作、校验引用并控制执行上限，不替模型选择业务答案。

## 4. 输入预处理

采纳“整合原始问题与对话历史，生成无歧义独立查询”的建议。

系统保留两份输入：

- `original_question`：用户原始问题，确保原始意图不会因改写丢失。
- `standalone_query`：结合必要对话历史生成的独立查询，用于解决指代消解和上下文追问。

示例：

```text
历史：远程办公制度适用于哪些员工？
当前：那试用期员工呢？
独立查询：试用期员工是否适用远程办公制度？
```

真实模式由模型完成改写；离线模式只支持验收案例需要的有限指代消解，并在文档中明确其能力边界。Trace 记录改写结果和简短的可审核依据，不记录模型内部思维过程。

## 5. 路由判断

调整后采纳“初步识别问题类型”的建议。

路由器只允许识别以下类型：

- `knowledge_query`：业务知识问题，必须进入检索。
- `clarification_response`：用户正在补充上一轮所需信息。
- `non_question`：问候或无法识别为知识查询的内容。
- `invalid_input`：空输入或格式异常。

路由器不能直接回答制度或产品事实。所有业务事实问题即使模型看似知道答案，也必须经过资料检索，避免路由误判导致模型凭记忆作答。

## 6. 模型接入

统一定义 `DecisionModel` 接口，由模型返回结构化动作：

- `search_docs`：检索文档。
- `read_doc`：读取候选文档的原文片段。
- `ask_user`：适用范围不明确或存在无法裁决的冲突时追问。
- `finish`：生成有依据的最终结果。

提供两种实现：

### 6.1 真实模型

`OpenAICompatibleModel` 调用真实模型服务。模型根据问题、历史、已执行动作和工具观察选择下一步，通过环境变量配置服务地址、模型名称和密钥。

### 6.2 离线 Mock

`OfflineMockModel` 在没有密钥时提供可重复运行入口。它根据结构化工具结果走不同分支，用于验证执行循环、工具调用、任务状态、错误处理和引用校验。

离线 Mock 只证明工程流程能够运行，不能证明真实模型的决策质量。README、评估文档和示例结果必须明确标出这一边界。

## 7. 混合检索

采纳并增强混合检索建议。计划组合以下可解释信号：

1. 精确词语匹配。
2. BM25 风格的关键词评分。
3. 中文字符二元组和三元组匹配。
4. 领域同义词与常见改写扩展。
5. 标题、适用范围、关键词、版本日期等元数据加权。
6. 多路候选结果融合排序。

暂不引入向量模型，原因如下：

- 离线评审环境不一定能下载 embedding 模型。
- 合成知识库规模较小。
- 关键词、字符片段和领域同义词组合足以覆盖本题验收场景。
- 检索分数和命中原因更容易解释与复现。

实现中保留 `Retriever` 接口，后续可增加向量检索而无需修改 Agent 主循环。

搜索工具只返回候选文档 ID、版本日期、相关度、匹配原因和非权威摘要。搜索结果不能直接作为最终引用，Agent 必须继续调用原文读取工具。

## 8. 知识库格式

采用本地 JSON 合成资料，主要字段包括：

- `document_id`
- `title`
- `version_date`
- `effective_from`
- `effective_to`
- `scope`
- `priority`
- `supersedes`
- `rule_overrides`
- `keywords`
- `content`
- `chunks`
- 片段级 `required_evidence_refs`，用文档 ID + 片段 ID 显式声明跨章节或跨文档证据依赖；兼容旧 `required_chunk_ids`

这种格式便于替换文档内容、制造版本冲突、注入适用范围差异、精确校验引用，并保证示例不包含真实企业隐私数据。

## 9. 证据校验与补充检索

采纳证据充分性校验建议。执行过程为：

1. 搜索工具发现候选文档。
2. 模型选择需要读取的原文片段。
3. `read_doc` 返回可引用原文。
4. 模型判断证据是否足够回答。
5. 证据不足时，模型改写查询、增加限定条件或扩大检索范围。
6. 补检索后仍无足够资料时，停止并报告资料缺口。

补充检索、读取原文和停止均属于模型基于观察结果选择的动作，是核心 ReAct 动态决策路径。

## 10. 冲突检测与元数据裁决

采纳冲突检测建议，但限制自动裁决条件。

只有存在明确规则时，系统才能依据元数据自动裁决，例如：

- 文档通过 `supersedes` 明确声明替代旧制度。
- 特例规则通过片段级 `rule_overrides` 明确声明覆盖一般规定，范围是严格子集，且问题明确命中特例范围。
- 文档显式给出优先级，且冲突资料适用范围相同。

不能仅因某份文档的版本日期更新，就推断它自动覆盖旧文档。新文件可能只是补充制度，日期本身不是充分的优先级证据。

无法可靠裁决时，系统必须输出：

- 发生冲突的文档 ID 和版本日期。
- 各文档对应的冲突原文。
- 具体冲突点。
- 无法自动裁决的原因。
- 需要用户确认的适用制度、人员范围或业务场景。

系统不得静默选择其中一个答案。

## 11. 分支决策

采纳建议中的四类主要分支，并增加执行上限分支：

- 证据充分且无冲突：生成带原文引用的回答。
- 冲突可由明确元数据裁决：说明裁决依据后回答。
- 冲突无法裁决：返回 `needs_clarification` 并请求用户确认。
- 无有效证据：返回 `insufficient_evidence`，明确资料缺口并拒绝编造。
- 工具首次失败：由模型根据观察决定是否重试或更换检索方式。
- 工具重试仍失败：返回 `tool_error`，不凭模型记忆回答。
- 达到执行步数或工具调用上限：返回 `max_steps_exceeded`，明确标记任务未完成。

## 12. 结构化回答与引用校验

采纳“所有事实都应有证据”的目标，但不承诺单靠字符串程序能够形式化证明任意自然语言与原文之间的语义蕴含。

模型输出改为结构化事实声明：

```json
{
  "claims": [
    {
      "text": "费用应在发生后 30 天内提交。",
      "citation_ids": ["C1"]
    }
  ],
  "citations": [
    {
      "citation_id": "C1",
      "document_id": "D01",
      "version_date": "2026-01-01",
      "effective_from": "2026-01-01",
      "effective_to": null,
      "quote": "员工应在费用发生之日起30天内提交报销。"
    }
  ]
}
```

程序层强制校验：

1. 每条事实声明至少绑定一条引用。
2. 被引用文档已经通过 `read_doc` 读取。
3. 引用片段逐字存在于对应文档原文。
4. 文档 ID、版本日期和片段位置一致。
5. 搜索摘要不能充当原文引用。
6. 已发现的冲突证据不能被遗漏。
7. 校验失败时打回模型修正，超过限制后返回明确的未完成状态。

真实模型模式可再增加一次“声明是否受到引用支持”的证据审查。该审查用于降低风险，不等同于数学或形式化证明。

## 13. 输出协议

最终输出至少包含：

- `answer`：回答、追问或错误说明。
- `claims`：结构化事实声明。
- `citations`：文档 ID、版本日期和原文片段。
- `gaps`：资料缺口。
- `conflicts`：发现的制度冲突及裁决情况。
- `status`：任务状态。
- `trace`：完整执行记录。
- `tool_calls`：工具调用次数。

任务状态包括：

- `completed`
- `needs_clarification`
- `insufficient_evidence`
- `tool_error`
- `max_steps_exceeded`

## 14. Trace 设计

每一步至少记录：

- 步骤编号。
- 模型选择的动作。
- 工具名称与参数。
- 工具返回摘要。
- 后续动作。
- 简短、可审核的决策依据。

Trace 不记录模型内部思维过程，只记录足以解释系统行为的行动依据。

## 15. 测试方案选型

测试使用 Python 标准库 `unittest`，通过以下命令运行：

```bash
python -m unittest discover -s tests -v
```

选择原因：

- Python 自带，不依赖联网安装。
- 支持临时替换知识库。
- 支持注入工具失败和模型动作。
- 适合检查执行轨迹而不仅是最终文本。

测试将验证：

- 是否调用正确工具并读取引用原文。
- 明确答案是否受引用支持。
- 冲突时是否列出冲突并追问。
- 资料外问题是否拒绝臆答。
- 改写问题是否召回正确资料。
- 上下文追问是否生成正确独立查询。
- 工具失败后是否重试并正确降级。
- 替换文档内容后，答案和动作是否随资料改变。
- 达到调用上限后是否返回明确的未完成状态。

## 16. 总体链路

```text
原始问题 + 对话历史
        ↓
生成独立查询
        ↓
轻量路由
        ↓
混合检索
        ↓
模型选择读取哪些原文
        ↓
证据充分性检查
   ┌────┴─────────┐
不足             充分
 ↓                 ↓
补充检索       冲突检测与元数据裁决
                   ↓
          回答 / 请求确认 / 拒绝臆答
                   ↓
           声明—引用程序校验
                   ↓
             输出结果与 Trace
```

## 17. 已知取舍与限制

1. 本地混合检索不是向量数据库，对开放领域的复杂语义改写能力有限。
2. 领域同义词可覆盖本项目合成资料和验收案例，但不是通用语义检索的替代品。
3. 离线 Mock 能证明工程链路和分支行为，不能代替真实模型决策效果评估。
4. OpenAI-compatible 接口覆盖面较广，但不同供应商的结构化输出能力可能不同，执行器仍需执行 JSON 格式和引用校验。
5. CLI 满足本项目可运行、可复制和可测试的要求，因此不投入 Web 界面与线上部署。
6. 程序可以严格验证引用来源和绑定关系，但无法单独形式化证明任意自然语言事实与证据之间的全部语义关系。
