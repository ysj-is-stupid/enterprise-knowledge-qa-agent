# 企业知识问答 Agent：总体方案

## 1. 方案目标

系统不是一个依赖模型记忆的通用聊天机器人，而是一个以企业资料为唯一事实来源、可展示证据和执行过程的知识问答 Agent。

总体方案围绕三条原则设计：

1. 先找证据，再生成结论。
2. 模型决定下一动作，程序守住引用、冲突和执行预算边界。
3. 无法可靠回答时，明确追问、报告缺口或失败，而不是补写一个看似合理的答案。

## 2. 总体边界

系统接收当前问题和可选对话历史，访问本地合成知识库，输出回答、引用、资料缺口、冲突、状态和 Trace。

系统内部可以调用真实模型或离线 Mock，但两者使用相同的动作协议、工具协议和安全校验。这样可以在无密钥环境验证工程流程，也可以接入真实模型评估动态决策能力。

## 3. 总体模块

### 3.1 CLI 与输入层

职责：

- 接收问题、对话历史、模型模式、知识库路径和执行预算。
- 校验空输入和参数格式。
- 将最终结果以人类可读格式或 JSON 输出。

### 3.2 查询理解层

职责：

- 保留原始问题。
- 选取必要对话历史。
- 生成无歧义的独立查询。
- 对输入作轻量路由。

路由不会回答业务事实，只决定是否进入知识检索、是否把输入视为澄清回复，或是否因输入无效直接结束。

### 3.3 决策模型层

职责：

- 观察当前查询、搜索结果、已读证据、工具错误、冲突提示和剩余预算。
- 在合法动作集合中选择下一动作。
- 为动作提供简短、可审核的行动依据。

决策模型可以是真实大模型，也可以是离线 Mock。执行器不根据业务关键词替模型预先确定整条动作路径。

### 3.4 ReAct 执行器

职责：

- 调用决策模型获取动作。
- 校验动作是否合法、参数是否完整。
- 执行搜索或原文读取工具。
- 把工具结果作为新观察写回状态。
- 维护步数与工具调用预算。
- 在模型请求完成时调用引用与冲突安全校验。
- 保存完整 Trace。

### 3.5 检索与工具层

提供两个核心业务工具：

- 文档检索：从知识库返回按相关度排序的候选文档及匹配原因。
- 原文读取：根据文档 ID 和片段标识返回可引用原文及元数据。

搜索结果只用于发现候选。只有原文读取结果可以进入证据集合。

检索器在计算词项统计、相关度和候选摘要之前，先根据请求者部门与文档 ACL 生成可见文档集合。权限上下文来自受信任请求对象，不属于模型可编辑的工具参数。

### 3.6 证据与冲突层

职责：

- 保存已读取的原文证据。
- 判断拟回答的关键条件是否具备证据。
- 发现同主题、范围重叠但结论不兼容的规则。
- 根据明确的替代关系、适用范围、优先级或特例关系提供裁决信息。
- 对无法裁决的冲突设置安全阻断。

### 3.7 声明与引用校验层

职责：

- 要求回答拆分为带引用 ID 的事实声明。
- 确认每条事实声明至少绑定一个引用。
- 确认引用来自已读取文档。
- 确认原文片段逐字存在且版本信息一致。
- 确认已发现的未裁决冲突没有被最终回答绕过。
- 将期限、金额和百分比规范化为结构化语义事实，确保数值与单位都受到原文支持。

校验失败后，将结构化错误作为新观察交还决策模型修正；超过预算仍无法修正时返回未完成状态。

### 3.8 输出与 Trace 层

职责：

- 统一生成回答、引用、缺口、冲突和任务状态。
- 保存每一步动作、参数、观察摘要、后续动作与行动依据。
- 支持输出到控制台和 JSON 文件，供测试及评审复核。

## 4. 总体数据流

```text
用户问题 + 可选对话历史
          ↓
输入校验与独立查询生成
          ↓
轻量路由：业务知识问题必须检索
          ↓
┌──────────── ReAct 决策循环 ────────────┐
│ 决策模型读取当前状态                    │
│          ↓                              │
│ 选择 search_docs / read_doc /           │
│ ask_user / finish                       │
│          ↓                              │
│ 工具执行或终止动作处理                  │
│          ↓                              │
│ 新观察写回：候选、原文、错误或校验失败  │
└───────────────↺────────────────────────┘
          ↓
声明—引用校验 + 冲突安全检查
          ↓
回答 / 请求确认 / 资料不足 / 工具失败 / 超限
          ↓
结构化结果 + Trace
```

## 5. ReAct 决策循环

### 5.1 初始状态

初始状态包含：

- 原始问题。
- 独立查询。
- 必要对话历史。
- 当前路由类型。
- 空候选列表与空证据集合。
- 空工具错误列表。
- 决策步骤和工具调用剩余预算。

### 5.2 合法动作

- `search_docs`：使用当前查询或模型改写后的查询检索候选。
- `read_doc`：读取某个候选文档的原文片段。
- `ask_user`：在适用范围或冲突无法判断时结束当前任务并请求用户补充。
- `finish`：提交结构化事实、引用、缺口和目标状态。

是否增加专门的验证或查询改写动作，将在阶段 3 结合接口复杂度决定；阶段 2 不固定具体参数结构。

### 5.3 每轮处理

1. 决策模型读取经过裁剪的当前状态。
2. 模型选择一个合法动作并给出行动依据。
3. 执行器校验动作和剩余预算。
4. 工具动作被执行，返回结果或结构化错误。
5. 观察结果追加到状态和 Trace。
6. 下一轮模型必须基于新观察重新选择动作。
7. 终止动作需要通过安全校验才能成为最终结果。

该设计确保至少存在“模型动作 → 工具观察 → 新模型动作”的闭环。

## 6. 证据充分性原则

阶段 2 采用以下总体判定原则：

1. 至少有一段已读取原文直接覆盖用户问题的核心结论。
2. 回答所需的适用对象、条件、时限或例外不能依靠猜测补全。
3. 高相关候选中存在潜在同主题文档时，应读取足够资料排除冲突。
4. 只有搜索摘要而没有原文时，证据不充分。
5. 原文只覆盖问题的一部分时，只能回答已覆盖部分，并把其余内容列为资料缺口。

具体评分阈值和算法留待详细设计与测试校准。

## 7. 冲突识别与裁决策略

### 7.1 冲突识别条件

当两份已读取资料同时满足以下条件时，系统认为存在潜在冲突：

- 讨论同一规范主题或同一产品问题。
- 适用范围相同、重叠或因元数据缺失而无法区分。
- 对时限、资格、额度、步骤或其他关键结论给出不兼容要求。

### 7.2 可以自动裁决的依据

- 文档明确声明替代另一文档。
- 文档存在明确且可比较的优先级。
- 用户场景只匹配其中一份文档的适用范围。
- 特例文档明确声明覆盖一般规则。

### 7.3 不能单独用于裁决的依据

- 版本日期较新。
- 检索得分更高。
- 文档标题看起来更正式。
- 模型认为其中一个规则“更合理”。

### 7.4 无法裁决时

系统不生成单一规则答案，而是列出双方原文、版本、冲突点与缺少的裁决信息，并通过 `needs_clarification` 请求用户确认。

## 8. 失败与预算策略

### 8.1 工具失败

工具异常被转换为结构化观察，不能直接导致程序崩溃。模型可以根据错误选择：

- 对暂时性错误重试一次。
- 调整查询或读取其他候选。
- 在无法核验资料时停止并返回 `tool_error`。

连续失败后禁止凭模型记忆作答。

### 8.2 模型输出异常

动作格式无效或参数缺失时，执行器返回格式错误观察，让模型在剩余预算内修正。持续无效则以未完成状态结束。

### 8.3 执行预算

初始限制为最多 10 个决策步骤、8 次工具调用、同一失败工具动作额外重试 1 次。达到上限后返回 `max_steps_exceeded`，并保留已经取得的证据和 Trace。

## 9. 任务状态

- `completed`：证据充分、引用校验通过且不存在未裁决冲突。
- `needs_clarification`：需要用户确认适用制度、范围或其他关键条件。
- `insufficient_evidence`：补充检索后仍没有足够资料。
- `tool_error`：关键工具持续异常，无法核验事实。
- `max_steps_exceeded`：达到执行预算，任务未完成。

空输入或非知识问题的具体状态命名将在阶段 3 统一，避免阶段 2 过早扩展最终协议。

## 10. 六类验收路径

### 10.1 明确答案路径

```text
独立查询 → 搜索命中唯一高相关候选 → 读取原文
→ 证据充分且无冲突 → 提交带引用答案 → 校验通过 → completed
```

证明点：回答依赖读取结果；文档内容被替换时，答案与引用随之改变。

### 10.2 文档冲突路径

```text
独立查询 → 搜索命中 D01、D02 → 读取 D01 → 发现另一高相关候选
→ 读取 D02 → 识别 30 天与 15 天冲突 → 无裁决元数据
→ 列出双方引用并追问 → needs_clarification
```

证明点：模型根据搜索结果继续读取第二份资料，没有擅自采用更新日期或更高分文档。

### 10.3 资料外路径

```text
独立查询 → 搜索无有效候选 → 模型扩大或改写检索词
→ 仍无有效候选 → 报告缺少相关资料 → insufficient_evidence
```

证明点：系统执行补检索，但不会将无关低分结果拼成答案。

### 10.4 相似问题改写路径

```text
口语化问题 → 查询归一化与同义词扩展 → 混合检索召回制度
→ 读取原文 → 生成引用答案 → completed
```

证明点：检索不只依赖问题与文档之间的完全相同措辞。

### 10.5 上下文追问路径

```text
对话历史 + “那试用期员工呢？”
→ 独立查询“试用期员工是否适用远程办公制度？”
→ 搜索与读取 → 回答已有证据或报告资料缺口
```

证明点：Trace 同时展示原始问题和独立查询，能够审查指代消解是否改变了意图。

### 10.6 工具失败路径

```text
模型选择检索 → 工具返回失败 → 模型观察失败后选择重试
→ 再次失败 → 明确无法核验资料 → tool_error
```

证明点：重试是模型收到错误观察后的下一动作；失败后没有生成业务事实。

## 11. Trace 总体要求

每一步记录：

- 步骤序号。
- 当前动作和动作参数。
- 工具返回摘要或终止动作结果。
- 下一动作。
- 简短行动依据。
- 决策步骤与工具调用剩余预算。

Trace 记录可审核的行动理由，例如“搜索结果包含两份同主题制度，需要读取第二份检查冲突”，不保存或要求模型输出内部思维过程。

## 12. 验证总体方案

验证分为三层：

1. 单元验证：检索、原文读取、冲突识别、引用校验、预算控制。
2. 链路验证：六类验收场景的完整 Agent 执行结果与 Trace。
3. 可变资料验证：临时替换文档内容，检查答案、引用、冲突状态和动作路径是否随之变化。

离线 Mock 用于稳定复现上述工程行为。真实模型运行记录用于观察模型决策效果，两者的结论必须在评估文档中分开陈述。

## 13. 方案取舍

### 13.1 保留原生执行器

原因是动作闭环、预算控制和引用阻断更容易直接展示，不需要为小型项目引入框架运行时。

### 13.2 不使用日期自动解决冲突

原因是发布日期不等于制度替代关系。错误地把“较新”当作“有效优先”会直接破坏冲突验收要求。

发布日期与生效日期也分开建模。检索器根据执行器提供的 `as_of_date`，先过滤尚未到达 `effective_from` 的规则以及已经超过 `effective_to` 的规则，再计算相关度。时间过滤只决定某日期下哪些资料可参与回答，不把日期新旧当作冲突裁决优先级。

### 13.3 不在路由阶段回答问题

原因是路由误判会绕过检索。路由只用于输入分类，业务答案必须来自已读证据。

### 13.4 不宣称程序可以完成绝对语义证明

程序严格检查事实—引用绑定、原文存在性和冲突阻断；真实模型模式可增加语义审查，但仍如实记录其非形式化验证边界。
