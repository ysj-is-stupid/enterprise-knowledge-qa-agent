# 企业知识问答 Agent：需求说明

## 1. 背景

员工在查询企业制度或产品规则时，常遇到资料分散、表述不一致、版本并存和上下文不完整等问题。普通生成式问答容易在没有资料支持时凭模型记忆作答，也可能忽略制度冲突或给出错误引用。

本项目建设一个可审计的企业知识问答 Agent。它必须先检索企业提供的合成资料，再读取原文、判断证据充分性与冲突情况，最后给出带原文引用的回答或明确说明无法回答的原因。

## 2. 用户与目标

主要用户是需要查询公司制度或产品规则的员工。

用户目标包括：

1. 快速获得明确、可执行的制度或产品答案。
2. 查看支持答案的文档 ID、版本日期和原文片段。
3. 在资料冲突时看到完整冲突，而不是得到系统擅自选择的结论。
4. 在资料不足或工具异常时得到明确边界，不被无依据内容误导。
5. 能通过连续对话追问同一主题，而不必重复完整背景。

## 3. 输入

单次任务接受：

- 必填：当前用户问题。
- 可选：此前对话历史，包括用户问题与 Agent 回答。
- 系统资料：带文档 ID、版本日期、适用范围等元数据的合成 FAQ 或制度文档。

输入预处理需要同时保留原始问题，并结合对话历史生成独立查询，用于处理指代和省略信息。

## 4. 输出

每次任务至少输出：

- 回答、澄清问题或失败说明。
- 结构化事实声明。
- 文档 ID、版本日期及逐字原文片段。
- 当前资料缺口。
- 已发现的文档冲突及裁决情况。
- 任务状态。
- 工具调用次数。
- 可审核的执行 Trace。

系统不得把检索摘要当作原文引用，也不得引用未实际读取的文档。

## 5. 功能范围

### 5.1 必须实现

1. 根据对话历史生成独立查询。
2. 对业务事实问题强制执行知识检索。
3. 从本地合成知识库混合召回相关文档。
4. 通过独立工具读取候选文档原文片段。
5. 由模型根据工具观察选择补充检索、继续读取、追问或停止。
6. 判断证据是否足以支撑回答。
7. 检测同主题、重叠适用范围下的不兼容规则。
8. 仅在存在明确元数据依据时自动裁决冲突。
9. 生成事实声明与原文引用的绑定关系。
10. 程序校验引用来源、原文真实性和声明绑定完整性。
11. 对工具失败执行有限重试并在持续失败后降级。
12. 设置模型决策步数和工具调用次数上限。
13. 支持真实模型与离线 Mock 两种运行模式。
14. 生成可保存、可比较的 JSON Trace。
15. 在检索评分前根据请求者部门过滤文档，禁止未授权候选进入模型上下文或 Trace。
16. 对声明中的期限、金额和百分比执行语义单位校验，禁止自然日、工作日等单位错位。

### 5.2 本期不做

- Web 界面或移动端界面。
- 线上部署和生产级运行时。
- 企业身份认证和外部身份提供商接入；本项目只接受调用方传入的部门上下文并执行文档 ACL 过滤。
- 多 Agent 协作。
- 向量数据库和大规模文档分片服务。
- OCR、PDF 解析和真实内部知识库接入。
- 对真实企业制度作法律或合规有效性判断。

## 6. 核心业务规则

1. 业务事实必须来自知识库证据，不能凭模型记忆回答。
2. 搜索结果只是候选，只有原文读取工具返回的内容可成为引用。
3. 每条事实声明必须绑定至少一条引用。
4. 引用片段必须逐字存在于对应文档中。
5. 仅有较新版本日期不能证明新文档覆盖旧文档。
6. 明确的 `supersedes` 可以裁决整份制度替代；特例覆盖必须显式绑定源与目标片段、范围为严格子集且问题明确命中特例范围；优先级只在适用范围相同时参与裁决。
7. 无法裁决的冲突必须完整展示，并请求用户确认适用制度或业务范围。
8. 没有有效证据时必须明确拒绝编造。
9. 工具失败后不得改用模型记忆回答。
10. 达到执行上限时必须以未完成状态结束，不能伪装成成功。

## 7. 必须验收场景

### 7.1 明确答案

输入命中一份内容明确、无同主题冲突的有效文档。

预期：Agent 搜索候选、读取原文，并返回 `completed`；答案包含文档 ID、版本日期和支持结论的原文片段。

### 7.2 文档冲突

两份制度对同一问题给出不兼容规则，且未提供适用范围、优先级或替代关系。

预期：Agent 读取双方原文，列出冲突内容和版本信息，返回 `needs_clarification`，不能擅自选择其中之一。

基准例：D01 规定报销期限 30 天，D02 规定 15 天，二者没有足以裁决的适用范围或优先级。

### 7.3 资料外问题

用户问题在知识库中没有相关证据。

预期：Agent 至少尝试一次合理的补充检索；仍无证据后返回 `insufficient_evidence`，说明缺少哪类资料，不生成事实答案。

### 7.4 改写后的相似问题

用户使用与文档不同的表达询问同一规则。

预期：混合检索能够通过字符片段、同义词或查询扩展找到正确资料，并完成原文读取与引用。

### 7.5 上下文追问

当前问题包含“那试用期员工呢”等依赖上文的省略表达。

预期：系统结合历史生成无歧义独立查询，再执行检索；Trace 同时保留原始问题和独立查询。

### 7.6 工具失败

检索或原文读取工具返回异常。

预期：模型观察到失败后选择一次重试或可行的替代动作；持续失败后返回 `tool_error`，说明无法核验资料且拒绝凭记忆回答。

## 8. 动态决策验收

至少提供两条不同的执行路径，证明下一动作会随工具结果变化：

- 路径 A：搜索命中唯一候选 → 读取原文 → 证据充分 → 完成回答。
- 路径 B：搜索命中相互冲突的候选 → 分别读取原文 → 无法裁决 → 请求确认。

另外还应展示：

- 无结果 → 扩展查询 → 仍无结果 → 报告资料缺口。
- 工具失败 → 重试 → 再次失败 → 降级结束。

仅有固定条件分支、自动重试或预设决策日志不视为满足动态决策要求。Trace 中的动作必须来自决策模型接口；执行器只负责动作约束、预算控制与安全校验。

## 9. 可替换资料验收

评审者替换某份文档中的关键规则后重新运行同一问题，系统应重新读取资料，并使最终答案、引用或后续动作发生相应变化。

验收要求：

- 答案中不得残留旧文档内容。
- 引用必须来自替换后的原文。
- 替换导致新增冲突时，状态应从 `completed` 转为 `needs_clarification`。
- 替换消除冲突时，系统可以在证据充分后完成回答。

## 10. 执行限制

初始方案采用双重预算：

- 最多 10 个模型决策步骤。
- 最多 8 次工具调用。
- 同一失败工具动作最多额外重试 1 次。

预算值将在详细设计阶段固化为可配置参数。达到任一上限后返回 `max_steps_exceeded`，同时保留已经获得的证据、资料缺口和完整 Trace。

## 11. 成功标准

项目完成时应满足：

1. 在 Python 3.11+ 环境按 README 命令可以离线运行。
2. 六类必须验收场景均有自动化测试和实际运行记录。
3. 至少三组输入、实际输出和 Trace 存放于 `examples/`。
4. 至少两组 Trace 明确展示因工具观察不同而选择不同后续动作。
5. 所有成功回答的引用均能在对应文档原文中逐字定位。
6. 文档冲突、资料不足和工具失败场景均不产生无依据事实答案。
7. 替换文档内容后，答案、引用或决策路径随资料变化。
8. 达到执行上限时返回明确未完成状态。
9. 真实模型不可用时仍可通过离线 Mock 验证工程流程。
10. 文档明确说明 Mock 结果不能证明真实模型决策效果。

## 12. 非功能要求

- 可复现：离线模式不依赖网络或密钥。
- 可审计：动作、工具参数、观察摘要和状态变化均可追踪。
- 可测试：知识库、模型和工具错误均可注入替换。
- 安全：不提交真实密钥、企业隐私或个人信息。
- 最小权限：文档必须显式配置部门 ACL，缺失 ACL 时拒绝加载。
- 可维护：模型、检索器和工具通过稳定边界解耦。
- 可解释：检索结果提供匹配原因，冲突裁决提供明确依据。

## 13. 假设与限制

- 输入资料为合成数据，不代表真实企业制度。
- 文档元数据可能缺失，因此系统必须允许“无法裁决”。
- 离线 Mock 只覆盖预设领域和验收案例，不具备通用语言理解能力。
- 本地混合检索适合小规模知识库，不代表生产级检索性能。
- 程序可严格验证引用来源和绑定关系，但不能形式化证明任意自然语言声明的全部语义正确性。
